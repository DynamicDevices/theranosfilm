A correction should leave a trace

Proposals stay proposals. A separate editorial record names the reviewed JSON digest, decision, reasons, sources and the GitHub discussion/revision. That is an accountable record—not proof that the contributor is a particular real-world person, or that acceptance makes a claim unquestionably true.

Two ways to contribute

  1. Open a source-backed evidence issue on GitHub. GitHub records the submitting account and discussion; you decide what to submit.
  2. Prepare one JSON proposal below and add it in a pull request under data/contributions/. Read the contribution rules and the schema.

No account or token is collected by this website. Nothing in the form is sent automatically, stored by this page or fetched from a submitted source URL. GitHub submission is a separate, explicit action.

How decisions and disputes work

  1. A proposal is validated as data, not accepted as fact. Public GitHub account history supplies attribution; profile fields alone do not.
  2. A maintainer records a separate decision using review.schema.json, the exact proposal hash and a source revision/discussion. Self-review under the same recorded profile is rejected. This check cannot prove distinct real people.
  3. Keep source support, counterevidence and reasons visible. Correct an existing record with a new proposal referencing supersedes; append a decision rather than overwriting history.
  4. Schema checks do not prevent a deceptive person inventing a different profile. Maintainers must check the actual GitHub provenance and evidence before publication; there is no automatic issue-to-accepted-fact importer.
  5. Privacy takes priority over preserving an exposed person's data. Report exposure without repeating the sensitive content; do not put secrets into public issues.
